# 缺口与待定项

按影响排序。**这一份是需要拍板的地方。**

## 1. 客户端分流规则不可管理

立项时用户的原话是「操作订阅的 Clash 以及 SingBox 的规则」。当前实现里,「规则」只有一层意思:**User-Agent → 返回哪种格式**。

客户端配置内部的分流规则(哪些域名走代理、哪些直连)是**写死在模板里**的:

- `settings` 表没有模板字段;
- `render.Clash(eps, meta)` **不接受模板参数**,规则完全写死在代码里;
- `render.SingBox(eps, nil)` 与 `render.Xray(eps, nil)` 的调用处一律传 `nil`,永远用内嵌的默认模板。

**要做的话大致是这个形状**(需要定):

1. `settings` 加「每个格式一份模板」;
2. CLI 能把模板取下来、改、传回去;
3. 模板里定义若干可被工具替换的位置(节点列表、规则列表、规则集地址);
4. 模板缺失时回落内置默认。

**待决策**:这是不是立项时要的「规则」?是就继续做;不是就把 [status.md](status.md) 对照表里那一行改成「显式不做」。

## 2. 经跳板机连节点做不到

`model.Node` 只有一个 `Address`,它同时在当两件事:

- 控制面 ssh 往哪连(`internal/node/ssh.go`);
- 订阅里发给客户端的地址(`internal/render/ir.go` 的 `endpoint()` → `ResolveExposure`)。

节点在跳板机后面时,这两件事不是同一个值:ssh 要连跳板机,订阅要发节点自己那个客户端能到达的地址。现在没有第二个字段可写。

**要做的话**:`Node` 加一个可选的 ssh 目标(空则用 `Address`),只有连接用它。需要定的是字段名,以及 `mpx node add` 怎么把它问出来。

**已经澄清的**:真实 SSH 传输验证过了(两台 Ubuntu 24.04 真机,`BatchMode=yes` 免密,控制面的 `HOME=/var/lib/mpx`,`node install` / `node sync` 都跑通)。原先「要不要加一个只连不写的探针」的问题,现在由 `node install` 的失败信息回答:连不上会直接报出来。

## 3. 单 token,没有管理员

对外多用户服务(上百至上千)只靠一个固定 token,意味着:

- 没有操作审计;
- 无法分权;
- token 轮换要改所有 CLI 的配置。

要不要引入管理员表,取决于这个控制面是否只有一个人操作。

## 4. `{USERNAME}` 只在订阅名里生效,在节点名里是空串

同一个变量名,两处行为不一致:

| 写在哪 | 结果 | 落点 |
| --- | --- | --- |
| 订阅名(`settings.profile_title`) | 展开成用户名,实测 `{USERNAME} 的订阅` → `alice 的订阅` | `internal/server/subscribe.go:171` |
| 节点名(`hosts.remark`) | **展开成空串** | `internal/render/ir.go:123` 写死 `"USERNAME": ""` |

而 `hosts.remark` 的 CLI 帮助与模型注释都写着「支持 `{USERNAME}` 等变量」(`internal/cli/host.go:26`、`internal/model/model.go:138`),`model.md` 也这么写了。**这是文档、帮助文案与实际行为的矛盾,不是有意设计。**

两种收法,得挑一个:

- **接上**:`Resolve` 本来就拿到了 `user`,把它透传给 `endpoint` 即可,一处改动。代价:节点名里带上用户名,截图分享时会泄露账号名。
- **撤下**:从帮助文案与文档里去掉对 `hosts.remark` 的承诺,只留 `{SERVER_IP}` 等无隐私含义的变量。代价:不能按用户区分节点名。

**待决策**:接上还是撤下?

## 5. HTTP 建用户的 `enabled` 零值是「停用」

`handleCreateUser` 直接 `decodeBody` 进 `model.User`,`Enabled` 是 Go 的零值 `false`:

```console
$ curl -X POST .../api/users -d '{"username":"dave"}'
{ "username": "dave", "enabled": false, "status": "disabled", ... }
```

而 CLI 显式传 `Enabled: !--disabled`,默认启用。**同一个字段两套默认值。**

这不算崩,但会咬人:手工调 API 或者以后写个前端,漏掉一个布尔字段就得到一批连不上的用户,而且不报错。

两种收法:

- **让默认一致**:`enabled` 用 `*bool`,nil 当 `true`(和 CLI 对齐)。代价:`model.User` 那个字段不能再是裸 `bool`,涉及序列化与存储。
- **让它显式**:保持零值语义,但在 handler 里要求请求必须带 `enabled`,不带就 400。代价:调用方多写一个字段。

**待决策**:哪一种?或者干脆不管,只在文档里写明?

## 6. 其他待定

| 项 | 现状 | 需要定什么 |
| --- | --- | --- |
| 订阅页 | 只返回配置,**没有** HTML 订阅页 | 要不要给一个能看到用量和到期日的页面 |
| 节点用量比例 | 没有消费系数,各节点流量直接相加 | 多节点成本不同时要不要加权 |
| 节点容错 | 单节点失败只记日志,不影响别的节点 | 连续失败要不要告警或摘除 |
| 数据导出 | 没有 | 备份/迁移是否只靠拷 SQLite 文件 |
| 用户自助改期 | 没有 | 续费是否只走 CLI |
| 入站 tag 冲突 | 未强制唯一 | 同一节点上两个入站撞 tag 会怎样 |
| `settings.rules` 顺序 | 按数组顺序匹配,顺序即优先级 | 要不要独立的优先级字段 |
