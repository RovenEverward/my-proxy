# 关键决策与理由

理由是承重的。只留结论,后来的人会把它当风格问题随手改掉。

## 1. 参考 Marzneshin 的模型,但不复用它的代码

目标里明确要求不复用,而且 Marzneshin 的状态机比这里需要的复杂(services 分组、host chains、node usage ratio、多管理员)。

**借的是模型而非实现**:五张表(外加后来自己加的流量采样表)、User-Agent 规则、订阅响应头这几处形状来自它;代码是全新的 Go。

## 2. 用系统自带的 `ssh` 可执行文件,不引 `golang.org/x/crypto/ssh`

一台机器怎么连(跳板机、`ssh-agent`、`~/.ssh/config`、`known_hosts`)在操作者机器上已经是既成事实。重写一份 SSH 客户端只多出一处会漂移的真相,还得把那些能力再补一遍。

## 3. 结构变更走 `node sync`,人员名单走周期收敛

- **结构变更**(加入站、改端口、换证书)必须重启 xray 才生效 → 人显式触发 `mpx node sync <id>`,全量下发 + 重启。
- **人员名单**(加人、摘人、到期、超限)走每轮增量收敛,只调 `xray api adu/rmu`,**不重启**。

理由:配额恢复和到期续费都会触发加用户。如果每次都重启,节点上所有人的连接都会跟着断一次。

## 4. 控制面启动时不下发配置

启动意味着重启 xray。控制面重启是常事(升级、改配置、机器重启),不该因此把每个节点上所有人的连接断一次。启动后自动做的只有人员名单收敛。

## 5. 只有控制面能 SSH,CLI 不能

能 SSH 到节点的是控制面那台机器,不是操作者手边这台笔记本。所以下发通道接在控制面进程里,CLI 只发 HTTP。

## 6. 单 token 鉴权

`/api/*` 走一个固定 Bearer token。没有管理员表、没有会话、没有权限分级。

**配套约束**:token 为空时完全不校验鉴权,因此这种模式只允许绑回环地址;绑非回环 + 空 token 会在启动时直接拒绝。

`/sub/*` 不鉴权 —— 订阅 token 即凭证。

## 7. 密钥派生用 SHA-256 域分隔 + X25519

不用 Marzneshin 的 `xxhash` / `nacl`,改用 Go 标准库:

- `derive(domain, key) = sha256(domain + ":" + key)`;UUID 取前 16 字节并补 RFC4122 版本位与变体位,密码取前 16 字节 hex。
- REALITY 密钥对用 `crypto/ecdh` 的 X25519。

理由:两边的 Key 体系本来就不通用,而标准库足够、零依赖。

## 8. 地址里的变量用用户名派生,不用随机数

`{SERVER_IP}`、`{USERNAME}` 这类变量要展开,`*` 要换成子域。这里的随机**必须由用户名派生**(`sha256("salt:" + username)` 取前 6 字节)。

用真随机数的话,客户端每次更新订阅都会看到新地址,配置里会堆满废弃节点。

## 9. 流量读累计值,上次值存在 `traffic_samples` 里

节点按 `email`(= 用户名)聚合流量分桶。控制面每轮读一次**累计值**(`statsquery` 不带 `-reset`),与该用户在该节点上的上次累计值相减,把差值累加进 `used_traffic` 和 `lifetime_used_traffic`;本次读数同时追加进 `traffic_samples`。

理由:`-reset`(读走即清零)看着省事 —— 读回的就是增量,控制面不用记住上次读到多少,也就没有「上次读数」这个会失步的状态。但 xray 的计数只在进程内存里,清零之后节点上就没有第二份:控制面漏采一轮、自己重启一次、或者采样间隔里 xray 崩过一回,那段用量就永远找不回来,事后还分不清是「用户没用」还是「账被吞了」。改读累计值之后:

- **上次值就是 `traffic_samples` 里该用户在该节点的最近一行**,是库里的数据 —— 控制面重启不丢,也不需要单独的状态字段;
- **两次读数相减得到增量**,少采几轮只是把增量并到下一次,不会丢;
- **读数变小 = xray 重启过**:记异常日志并按重启处理(本次读数成为新基准),不静默;
- 历史落表让用量可重算、可画曲线。

代价:多一张随采样线性增长的表,每轮每用户多一次读、有变化时多一次写。

## 10. SQLite 单连接 + WAL

纯 Go 驱动 `modernc.org/sqlite`(不引 cgo),连接池上限 **1 条**,`journal_mode=WAL`、`busy_timeout=5000`、`foreign_keys=ON`、`synchronous=NORMAL`。

理由:控制面是单进程,连接池 1 条就消除了写冲突;WAL 让订阅读取不被流量写入挡住。

**代价**:遍历 `*sql.Rows` 期间不能再发起查询,否则会等自己持有的那条连接而死锁。这条约束写在 `internal/store/store.go` 的包注释里。

## 11. 级联删除靠外键,不靠应用层

`ON DELETE CASCADE` 让 `DeleteNode` / `DeleteInbound` 各只需一条 `DELETE`。应用层逐表删是第二份真相,早晚会漏一张。

## 12. 订阅渲染与节点配置渲染不共用代码

两边的目标不同:客户端配置要的是「怎么连」,节点配置要的是「怎么被连」。硬合成一份会到处是 `if 是节点侧`。

但它们共用中间表示 `Endpoint` 之前的输入(同一个 `Resolve` 展开入口),所以「哪些 host 属于这个用户」这件事只有一份实现。

## 13. mpx 在节点上占自己的一份路径和服务名

核心 `/usr/local/lib/mpx/xray`、geodata 与核心同目录、配置 `/etc/mpx/xray/config.json`、服务名 `mpx-xray` —— 都不在 xray 的惯用位置上。

理由:一台机器上住着别人的 xray(Marzban 装的、手工装的)是常态。若用 `/usr/local/bin/xray` 和 `xray` 这个服务名,`node install` 会覆盖别人的核心、`node sync` 会重启别人的服务,而且谁覆盖谁取决于谁后跑 —— 等出问题时现场已经没了。分开之后两边各跑各的,代价只是多占一份磁盘。

**配套约束**:geodata 必须和核心同目录,因为 xray 只去二进制所在目录找 `.dat`。

## 14. 节点上什么都不用准备,包括出网

发布包由控制面下载一次、缓存在自己那边(`<库目录>/xray/<版本>_<os>_<arch>/`),再把 `xray` 和两份 geodata 推过 ssh 送过去。

理由:节点常常在很差的网络里,或者干脆没有出网权限。把「能拿到发布包」收在控制面做一次,节点上就只剩 sshd、systemd、coreutils 三样,不需要 curl、unzip,也不需要能连 GitHub。代价是安装那一次要推 65MB。

**版本不进库**:节点上装的是哪个版本,随时能从节点读出来(`xray version`)。存进库就是第二份真相,而且有人手动升过级之后它就错了。库里只记「用哪台机器、走哪条路」。

**重跑时只推变了的文件**:推之前先和节点对一次 sha256(节点上有 `sha256sum` 或 `shasum` 就用,一个都没有就跳过比对)。一个核心加两份 geodata 接近 65MB,而换一版核心通常只动其中一个 —— 这一步把「重装同一版」从等一次传输变成等一次握手。对不出来的情况一律当「不一样」重推:少推一个文件只是多等一会儿,推错一个装不起来。

## 15. 装和更新是同一条命令,而且都要能拒绝自己

控制面重复跑 `deploy/install.sh`,节点重复跑 `mpx node install <id>`。两条路不是重复劳动:控制面无法给自己装二进制,而节点只有控制面能 ssh 过去(见决策 5),所以脚本只能由人在控制面机器上跑,节点侧只能在控制面进程里跑。

两处都带同一套兜底,而且**过不了就什么都不换**:

- 换二进制前先跑一次 `--help`(跑不起来说明交叉编译的 GOOS/GOARCH 错了);
- 换核心前先拿节点上**现有的**配置试跑新核心;
- 下发配置后确认服务真的起来了,没起来就回滚到上一份并把节点日志带回来。

理由:这类替换失败的代价不对称 —— 换错了就没有控制面,或者节点上所有人的连接断掉;而拒绝替换只是这次更新没成。

## 16. 备份含库与系统 ssh 私钥,不含管理 token;恢复是「暂存 + 重启换入」

**备份内容**:gzip 过的 tar,包含 `manifest.json`(创建时间、控制面主机名、各表行数、是否含 ssh 私钥、表名清单,**不含任何密钥正文**)、一致快照 `mpx.db`、以及控制面连节点用的系统 ssh 私钥 `id_ed25519`(存在才放,0600 写进归档)。`users.key` 是派生订阅 UUID/密码的种子,恢复后订阅 token 不变、能继续出订阅 —— 这份归档等于一整套凭据。

**不放管理 token**:token 在 `/etc/mpx/env`,塞进归档等于把凭据复制进一个会被到处拷的文件。token 丢了重新配一次就行,而 `users.key` 和节点私钥丢了的代价是重配所有人 + 重新授权节点公钥。

**恢复是「校验 + 暂存」,真正换入在下次启动**:

- `POST /api/restore` 只做两件事:校验(gzip/tar 能解、有 `mpx.db`、manifest 能解析、库能开且是本系统的)+ 把校验过的库写到 `<db>.restore`(0600)。运行中的控制面不能安全替换自己打开的库文件,所以不当场换。
- `Serve()` 在打开数据库**之前**换入:存在 `<db>.restore` → 旧库(连带 `-wal`/`-shm`)改名 `<db>.pre-restore-<UTC 时间戳>` → 暂存文件改名 `<db>`。换入发生在打开之前,不会出现「半个库」;旧库留着可回退;没有控制面也能恢复(手动把 `mpx.db` 改名成 `<db>.restore` 再启动)。

## 17. 超时值由调用方定,兜底值只是保险

`SSH` 带一个 `Timeout`,但它的作用是「**保证没有任何命令能永远挂着**」,不是「规定每条命令该多久」。真正的 deadline 由调用点给:`SampleTraffic` 20 秒、`ReconcileUsers` 60 秒、`DeployNode` 2 分钟、`InstallNode` 15 分钟。`Run` / `RunWithInput` 里 **ctx 已经有 deadline 就不覆盖**,没有才套上兜底值 15 分钟。

理由:

- **只有调用方知道这条命令要多久**。同一条 ssh 通道上,「读一次 stats」是几百毫秒,「推 65MB 核心」是几十秒到几分钟。用一个统一值必然两头不对:取小了正常的安装被误杀,取大了卡住的采样白等十几分钟 —— 兜底值只该兜住「忘了给 deadline」这一种情况,按最慢的合法命令取(推 65MB 实测约 40 秒,按 100KB/s 的慢链路算约 11 分钟,留到 15 分钟)。
- **预算是「单个节点用掉的上限」,不是整轮的上限**。采样 20 秒压在 30 秒周期之内,是为了让一轮最坏情况下仍能跑完;一个节点把预算用完只记这一节点失败,后面的节点照常处理。
- **超时必须能和「连不上」分开**。两种情况要做的事完全不同(前者是节点卡住了,后者是网络/密钥/关机),而 `exec.CommandContext` 超时也是杀进程、退出码和 stderr 都可能是空白,所以报错先看 `ctx.Err()`:`DeadlineExceeded` → 「命令超时(节点卡住了)」,`Canceled` → 「命令被取消」,否则原样带 `ssh` 的 stderr。没给 deadline 的命令从日志上就能看出是超时还是不可达。

## 18. 不通的节点要退避,而不是每轮都重试

后台任务记住每个节点连续失败几次、下一次什么时候再试:失败后等 `30s × 2^(n-1)`,封顶 5 分钟,成功一次清零。退避窗口内整个节点跳过(采样和收敛都不做),窗口内的每一轮只记一条 `Info`,写明跳到什么时候。

理由:

- **重试的代价和成功的概率不成比例**。一台断电的节点每轮要花掉一整个采样预算(20 秒),而 30 秒的周期意味着几台不通的节点就能让循环永久落后 —— 那之后所有节点都在延迟里,连「通了」的那些也读不到准数。
- **跳过不会丢账**。批 1 之后采样读的是节点上的**累计值**,和上一次采样算差后累加:跳过几轮只是下一次的差大一点,总量一分不少(见决策 9)。而节点不可达时收敛本来也什么都做不了,所以整节点跳过是安全的。
- **失败越久退得越远,但不会不再试**。翻倍到 5 分钟封顶,做得是「刚挂的节点一分钟内恢复」(30 秒 / 1 分钟各试一次),同时把「关机维护」的节点压到每 5 分钟一次。

## 19. 心跳只在内存里,不落库

控制面记启动时间、最后一轮的起始与耗时、Tick 次数、每个节点的失败次数与暂停到什么时候,全部放在 `Task` 的字段里,用一把锁保护,经 `GET /api/status` 与 `mpx status` 读出来。**不写表。**

理由:

- **它是「现在」而不是「历史」**。这些值的全部意义是让人立刻看清当前状态;重启后旧心跳只会误导人。要历史的话,`traffic_samples` 那种表才是对的地方。
- **写库会把读状态变成写操作**。周期任务每 30 秒写一次表,和采样、收敛抢同一条 SQLite 连接(决策 10 只有一条),为一份没人回看的记录添了写放大和锁竞争;失败次数还带着「失败」这个会被反复覆盖的语义,落库就是一堆无用行。
- 代价是重启清零。这一条可接受:控制面刚起来时 `ticks=0`、`last_tick_at=null`,`mpx status` 直接说「还没跑过」,没有假装有历史。

## 20. 「我推了什么」和「现在是什么」分两张表存

- **基准**:`nodes.deployed_hash` / `deployed_at`,只在 `DeployNode` **成功之后**写。
- **观察**:`node_status` 表,每次检查覆盖一行(按 `node_id` upsert),**不碰 `nodes`**。

漂移 = 观察到的哈希 ≠ 基准。`!Deployed()`、没查过、连不上,一律**不算漂移** —— 那是「不知道」,不是「一致」。

理由:

- **两份值变化的原因不一样**。基准变是因为我下发了;观察变是因为节点上发生了什么(有人手改、文件被换、检查失败)。写在一行里,一次读不到或写失败就可能把基准盖掉,之后就再也比不出漂移,而且看不出来是被盖掉的。
- **「没有基准」必须是一种状态**。从没下发过的节点,拿观察值和空基准比会得出「被改过」这种刺眼的结论,而事实是什么都不知道。所以 `Deployed()` 是漂移判断的第一道门。
- 代价是判断漂移要读两张表。可接受:两张表都各只有一行。

## 21. 告警「报一轮、比一轮」:没问到的不算好

每个节点在内存里保留一份**上一轮报出去的告警 Key 集合**。一轮里按当前事实收集该报的 Key,末尾把「上一轮有、这一轮没有」的那些销掉(`Resolve`)。

**节点这轮没问到(不可达、或正在退避)时只加不减** —— 「看不到」不等于「好了」。

理由:

- **散在各处按条件销,必然对不上**。证书告警的 Key 里带证书路径(一张证书一个 Key),而销的那一头只拿得到节点 —— 这一版最初就是这么写的,结果是证书告警报出去之后永远销不掉:证书续了、文件删了、入站都删了,日志里那一条还挂着。
- **网络抖一下就该安静**。如果「这轮没查」也算恢复,一次 ssh 超时就会刷出一串「已恢复」,下一轮又全部重新报;真出问题时这些噪声会把有用的那几行淹掉。
- 反过来,节点恢复后所有告警在同一轮里被销掉,这也是对的:它们本来就是同一件事的几面。

## 22. 巡检第一次就跑,而且整轮有上限

节点状态巡检每 10 个 Tick(约 5 分钟)一轮,但**第 1 个 Tick 也跑**;整轮套一个 45 秒的预算,用完了就把剩下的留到下一轮,并记一条日志。

理由:

- **最需要答案的时刻是刚起来的时候**。才启动的控制面 `mpx node list` 里全是「未知」,而按「第 10 个 Tick 才跑」要空等 5 分钟 —— 恰恰是刚改完配置、最想确认的时候。
- **巡检是顺路做的事,不能反过来压住主线**。采样、到期、收敛共用一个 30 秒周期;单台节点各有 30 秒预算,十几台慢节点串起来就是好几分钟,采样被推后之后读到的数也跟着变糙。给整轮设上限,是承认「这一轮查不完」比「这一轮什么都晚」好:没查到的节点保持上一轮的状态,下一轮继续。
- 45 秒和单台 30 秒一样是经验值(十几台通常查得完、又不至于压住下一轮),不是算出来的。

## 23. 自检只有 fail 才让退出码非 0

`mpx doctor` 有 fail → 退出码 **3**;只有 warn → 退出码 0。一台节点只出一行结论,按**最重的那条**定,所有发现写进同一行。

理由:

- **它要能当健康检查用**。脚本拿 `$?` 判断,所以「查成了、系统有毛病」得和「没查成」(连不上控制面、参数写错,退出码 1)分开 —— 后者重试一下可能就好了。
- **warn 全算失败等于天天报警**。没下发过配置、控制面还没接后台任务,这些都是「该看一眼」;把它们算成故障之后,这个命令很快就会被人忽略。
- **一行一个结论,按最重的算**。一台节点可能同时漂移、证书快到期、服务没在跑;分成多行会让同一台机器在表里占好几行,反而看不出「这台整体什么状况」。所以结论取最重的那条,提示优先用最重那条自己给的。
