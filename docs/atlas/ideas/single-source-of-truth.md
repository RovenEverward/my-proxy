# 唯一真相，节点是执行器

> 待确认：Agent 从 [设计](../../design.md) 与 [关键决策与理由](../../internal/decisions.md) 第 3、9、12、14、20 条提炼，请主人确认说法。

> **30 秒版**：所有「谁在哪、还剩多少、该长什么样」只存在控制面的一份库里。节点不保存任何判断，只执行控制面算好推过来的东西。这样真相不会散，改动只牵连该牵连的人，账也不会丢。

## 从一个场景说起

alice 这个月超了 100GB。手工时代，要有人记得去算、登上她用的每台机器删掉她、下个月再加回来，中间任何一步忘了，她要么一直能用，要么一直连不上还不知道为什么。在 MPX 里，这件事没人去做：控制面每 30 秒算一次她该不该在，节点上多了就摘、少了就加，她的订阅自动变成写着「已超限」的占位节点。

## 这个想法是什么

**真相只有一份。** 节点、入站、入口、用户、规则住在控制面的 SQLite 里，CLI 不缓存，节点上的配置文件是全量渲染出来的，不是手工维护的。任何一处想知道真相，都去问控制面。

**节点是执行器，什么都不装。** 控制面用系统自带的 `ssh` 和 xray 自带的 API 驱动节点：下发配置、增删用户、读计数。节点不跑 MPX 组件，不主动联系控制面，也不需要能出网。换来的是节点零维护；代价是拿不到结构化状态，要问就得 ssh 上去执行命令。

**按改动的性质分路。** 改结构（端口、入站、证书）全量下发并重启；改名单（加人、摘人、超限、续期）走周期收敛、只调 API。分开是因为名单变化远比结构频繁，每次都重启会把一台机器上所有人的连接断一次。

**账不会丢。** 流量读累计值，上次读数存在库里，漏采、控制面重启、xray 崩过，下一次差值都能补回来；读数变小说明节点重启过，记一条异常而不是吞掉。「我推了什么」和「现在是什么」分两张表存，巡检一比就知道有没有人动过节点。

## 它带来什么、代价是什么

换来：节点挂了不影响订阅，控制面挂了不影响已连上的用户，开销不随流量增长。代价：改结构必须重启；写入串行，规模上限在一台机器；两套渲染（订阅和节点配置）各自维护。
